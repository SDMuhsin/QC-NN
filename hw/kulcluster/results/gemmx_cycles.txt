Interpretation
* True accelerator time in-chimera: the GeMM core is busy 40 cycles (probe == BlockGemm perf
  counter): 36 back-to-back MAC-array A/B fires (= ideal, the array never stalls) + 2 add-C
  cycles + 2 cycles state/drain -> 90% MAC utilisation. The SIMD rescale stage trails by 11
  cycles (GeMMX CSR counter 51 -> 71%). Standalone the same counter reads 55 (65.5%): there the
  GeMMX start follows the streamer start by 1 cycle, so the GeMM waits ~4 cycles for the first
  streamer data (est. GeMM core 44 cycles, 82%). The 82-99% of the OpenGeMM/SNAX papers is for
  larger workloads; at K=18, M*N=2 the fixed add-C/fill/SIMD-tail cycles weigh more.
* Streamer counter 76 (chimera) vs 56 (standalone): in chimera the streamer is started 25 cycles
  before the GeMMX (one instruction fetch apart) and is busy-waiting for it; 76 - 25 = 51 = GeMMX.
* The 330-cycle "accelerator window" (kul_result[2] = t3 - t2) is software time. Core 0 runs
  from the memory island and every instruction costs ~25 cycles to fetch. The window holds about
  13 instructions (start CSR writes, call, 2 dummy streamer-CSR writes, the busy polls, a CSR
  write, ret, mcycle read) = 13 x 25 = 325 cycles. The accelerator is done 103 cycles after t2 (GeMM
  51..91, SIMD ..102, streamer ..103) and the first busy poll (at 178) already reads idle, so the
  remaining ~227 cycles are instruction fetch only. The ~71-cycle standalone window is the
  same code with ~1-cycle instruction fetch in the SNAX TB, which is close to the
  accelerator time.
* Setup and copy-in overhead: programming the CSRs costs 12275 (streamer) + 3530 (GeMMX) = 15805
  cycles in chimera vs 1540 + 444 = 1984 standalone (same code, fetch-bound). The copy-in is
  722630 cycles in chimera (core-0 byte/word loop over the narrow AXI from the memory island,
  1152+2304 int8 + 128 int32 elements) vs 176 cycles with the cluster DMA standalone. Per run, the accelerator's
  40-cycle GeMM is about 0.005% of the in-chimera kernel time.
