# R49: act hold-step DRT-0218 "Guide is not connected to design" - root cause and fix

Labels: [M] measured, [S] from OpenROAD source (commit 01bba3695 = our build 2.0-12381), [E] estimate.  Times UTC.
Host tau6 only (tau4 down; hub DR + queue running there, left alone; all R49 jobs < 7 GB RSS).  $B =
/tmp/ckp908/qc18bacc/build.  Probe scripts and logs: tau6 /tmp/ckp908/r49 (236 kB; probe dbs deleted).  Nothing committed.

## 1. Bug (confirmed)
**The routed db that the hold step loads (db/finish.odb) still holds the pin access points of the route step's detailed
route, OpenROAD's odb keeps them unchanged when a cell is resized, moved or flipped, and global_route places the pins at
those stale access points.**  A resized cell's pin is then placed where the OLD master's pin was.  The guide misses the
real pin, and DRT either patches the gap (DRT-1000, only if a guide is within one gcell) or stops (DRT-1001 -> DRT-0215 /
0224 -> DRT-0218).

Chain [S]:
* GRT `GlobalRouter::pinAccessPointPositions` (src/grt/src/GlobalRouter.cpp:579-621) uses
  `dbITerm::getPrefAccessPoints()`; when that is empty it uses every access point of the instance's class
  (`getAccessPoints()`, indexed by `dbInst::pin_access_idx_`).  The position is the instance location + the stored
  offset, transformed with R0.  It uses the pin-shape centre only when neither exists.
* odb never invalidates these.  `dbInst::swapMaster` (src/odb/src/db/dbInst.cpp:1145-1295) remaps the iterm -> mterm
  index but leaves `_dbITerm::aps_` (keyed by the OLD master's dbMPin id) and `pin_access_idx_` unchanged.
  `setLocation` / `setOrient` keep both [M, p2.tcl].  `dbInst::create` sets `pin_access_idx_ = 0` (dbInst.cpp:129), i.e.
  class 0 of the master, whatever its orientation.
* DRT recomputes pin access itself (FlexPA, TritonRoute.cpp:892-898), so it sees the real pins.  Its guide check
  (checkPinForGuideEnclosure, io_guide.cpp:267-293) needs the pin shape to overlap a guide on the pin layer.  `patchGuides` (io_guide.cpp:77-153)
  looks only at the 4 neighbouring gcells.  No guide there -> DRT-1001, the pin is never reached -> DRT-0218
  (io_guide.cpp:956).

Why only the act hold step fails: the route step routes cts_rt.odb, which was never detailed-routed (no access points),
so GRT uses the pin shapes: 0 DRT-1000 and 0 GRT-0350 in r48_act/openroad.log [M].  The hold step loads finish.odb, which
has access points for all 570 550 instances (pin_access_idx >= 0 [M]); its DRV repair resizes about 3 000 cells
(upsizes, with wider pins).  The column eco rounds show the same mechanism without failing: 20 / 26 / 58 DRT-1000 in
r48_col r35_hold.log / _r2 / _r3 [M]; every pin there stayed within one gcell of a guide.

**Where:** an OpenROAD bug (odb does not invalidate access points on swapMaster / setLocation / setOrient / create, and
GRT trusts them).  Our flow triggers it by running a global route on a db that was detailed-routed before, after an ECO.
Upstream flows do not do this.  It is not in our constraints or scripts.

## 3. Fix (in the flow)
* New `route/pa_reset.tcl` (`qb_pa_reset`).  It runs after the last placement or netlist change and before global_route.
  For every instance it sets `pin_access_idx` out of range, so `getAccessPoints()` returns nothing.  For every pin it
  clears the preferred APs with `setAccessPoint <mpin> NULL`, first using the current master's dbMPins and then, for keys
  left from an old master, the dbMPin list of the largest master (dbMPin ids are 1..n per master and the Tcl API has no
  getId).  It prints `QB_PA_RESET insts / pins_with_preferred_ap / left` (r48_act replay: 258 011 / 898 914 / **0**).
  GRT then uses the pin shapes, as in the route step.  DRT recomputes pin access for every instance anyway (it overwrites
  `pin_access_idx`, FlexPA_unique.cpp:260) and writes it back to the db.
* Sourced in `repair/hold_eco.tcl` before its global_route (every block's hold / ECO step: act, column, hub) and in
  `route/reroute.tcl` (same pattern).  The headers of both are updated, and the flow/README.md act line points here.
* Is it a band-aid?  It works around an OpenROAD bug whose cause is known (sec. 1).  It hides nothing of ours: it deletes
  data the tool keeps stale and the router rebuilds anyway.  Removing it is the right move only after an OpenROAD update
  that invalidates access points on swapMaster / setLocation / setOrient.
* Not changed: the act route step (no stored APs) and the top flow (global_route on grt dbs only).  The
  `signoff/antenna.tcl` R29_GRT path runs on a grt db.

## 4. Also found while replaying (not fixed)
* [M] **The act hold repair does nothing with the current order (DRV first, R48).**  repair_design (qc_repair_drv,
  -max_utilization 90) inserts 520 buffers and resizes 3 064 cells.  The following `repair_timing -hold -max_utilization
  95` then finds 2 948 hold endpoints and stops at once with RSZ-0050 "Max utilization reached", inserting 0 hold buffers
  (hold after the repair: -0.058 ns / 43 endpoints, unlegalised).  Try 4 (hold first) inserted 2 791 hold buffers.  [E]
  cause: the DRV upsizing pushes the resizer's design area past the 95 % cap.  Not checked; it needs the design area /
  core area of the act at that point.  So the act hold step will route cleanly with the fix but will not repair hold
  until this is resolved.
* The GRT-0350 "Missing route to pin" warnings (873 / 887 / 887 / 924 in act tries 1-4, 0 in the route step [M]) come
  from the same stale data.  The parasitics estimate (MakeWireParasitics.cpp:422-451 [S]) puts the pin at the first
  stored AP, while the route used the voted position.  So the post-GRT timing of those tries (h35 after_legal_grt_est)
  also used wrong pin positions [E].  With the fix: expected 0 [E]; not measured, because the A/B GRT ran without STA.
