## Bug 1 (own setup, fixed in round): PT saw no free site
The first DMSA run fixed DRV but fix_eco_timing -type hold made **0 changes** (239 endpoints left). phys_ff.log showed
"Identified standard filler cells 0" because the kit's DCAP*/FILL* are not PT standard fillers, so every row site
counted as occupied. A single-corner, non-physical PT test fixed all 240 with BUFFD1, which isolated the cause. Fix:
`set_eco_options -filler_cell_names $QC_PNR_DCAP $QC_PNR_FILL`, after which 272 392 fillers were recognised. That change
list was never applied (ICC2 killed before save), so the ECO below is still the one and only round.

## Gate: ff hold not 0 -> binned, no second round [M]
All 12 are direct flop-to-flop paths (CP -> Q -> D, fanout 1, no ECO cell on the path). None of them was among the 239:
pre-ECO (r55) slack was +0.1 .. +2.3 ps, and PT fixed only slack < 0 (no margin). All 12 sit 1-9 um from an inserted
ECO cell. Two bins:
1. **Data net re-routed shorter by route_eco (11 / 12)**: data arrival -0.1 .. -2.6 ps, clocks unchanged within 0.2 ps.
   Q-net wire cap fell (e.g. g_wq_1 t1_reg_12 -> t2_reg_12: 1.86 -> 0.54 fF). DEF: the r55 route had a detour (up to
   y 104.8 and back), r56 is direct. The cells did not move, so route_eco's detail-route DRC repair around the new
   cells re-routed unmodified neighbour nets.
2. **Capture-clock branch slower (1 / 12)**, g_fq_1..g_fi_4 rmid q_reg_7: data unchanged, capture latency +4.2 ps at the
   leaf CKND8 cts_inv_32429549 -> CP. Leaf-net total cap only +0.3 fF, so it's the branch to this sink (re-routed),
   not the load.
Why one round can't reach 0 here: the ECO's own local re-route moves near-critical (0..+2.3 ps) neighbours by up to
~4 ps, and PT's ECO timing assumes unmodified nets keep their parasitics. Candidate methods (decision for the PI,
not taken): a hold fixing margin covering the measured perturbation (~5 ps, `-hold_margin` / `set_eco_options
-timing_hold_margin`), and/or `route_eco -reroute modified_nets_only` so neighbours are not touched.
