# R30 — hub routing failure / slowness: root cause
Measurement and A/B only. No default changed, nothing committed. Scripts in impl/r30/. They are read-only probes, and no db is written:
net30.tcl, pdn30.tcl, plc30.tcl, dens30.tcl, bin30.tcl, dnt30.tcl, grt30.tcl (verbose GRT), dr30.tcl (GRT + short DR A/B),
drc30.py (marker classes), bins30.py (markers per density class). Hosts: tau6 (r29_hB), tau5 (r28_h125, r24_d65t, pe_c), tau4 (r26_p1).

## 1. The defect [M]
The flow gives the global router a capacity model that the detailed router cannot meet. GRT derates every layer
M2-M9 by only 0.25 (`hub.cfg` `GR_ADJUST 0.25`, `route.tcl`), and the hub runs then lower M5-M9 to 0.10 (`QB15_GADJ_L`,
r21/r22/r28/r29 run scripts). So GRT may fill 75 % of every M2 / M3 track with through-routes. In the standard-cell area,
M2 is the pin-access layer: every M1 pin needs a VIA1 landing and an M2 stub to reach M3. GRT does not see that use
(pins are gcell nodes to GRT). The GRT result looks clean (0 overflow, 27.8 % average usage on h125), but its guides
put through-traffic on M2 / M3 tracks that pin stubs already use. The detailed router then spends its iterations
ripping up M2 shorts. This is the "pin-density stall" of R25 / R27 (M2 / M3 / VIA1 markers that follow pin density),
and it is what made the 1.0x die look unroutable.
History: the adjustment came down over the rounds to make GRT clean (lib default 0.3 -> core / slice 0.25 -> 0.15 ->
M5-M9 0.10, act 0.05; R15, R17). Each step moved congestion out of GRT, and so out of the R22 budget gate (which
measures cuts against the same 0.25 / 0.10 capacity), into DR.

## 3. Ruled out [M]
- Tracks: every layer's track grid equals the LEF pitch and offset, and the std-cell M1 pins sit on the M2 tracks (ND2D1 A2 / A1 / ZN at
  x 0.1 / 0.5 / 0.7). An 0.1 horizontal offset is worse (2.4). Rows: 1 781 rows, site 0.2 x 1.8.
- Placement: all 338 312 std cells (h125 grt) are PLACED on a row origin, with the row orientation, on the site grid.
- Netlist: no undriven multi-pin net, no dont-touch net or instance left in grt.odb; 2 309 tie cells.
- PDN: core grid M1 rails + M1->M4 stacks (145 830, M2 pad 0.30 x 0.18) + M4->M7 stacks (17 615) + M7 / M8 / M9 straps.
  Cell rails are 0.33 wide like the followpins. Removing every PG via in the PE A/B changes nothing. On the hub, PG-related
  M2 shorts are < 1 %.
- LEF copy (lef_pnr.py) drops only the M1 MINIMUMCUT lines. Pin access: 0 pins without an access point.
- DR environment: route.guide matches the db (3 927 772 guides), 16 threads on 8 cores / 16 HT (880 % CPU), 21 GB peak, no swap.

## 4. Fix (opt-in, not applied; defaults unchanged)
Derate the pin-access layers in GRT: `QB15_GADJ_L` takes extra pairs (e.g. `"M2-M3 0.6 M5-M9 0.10"`, applied after
the uniform call by the existing r21 wrapper; e.g. `QB15_GADJ_L="M5-M9 0.10 M2-M3 0.6"`), or set `GR_ADJUST` per layer in `route.tcl`. dr30.tcl `R30_GADJ` is the
same thing for a GRT re-run. With M2 / M3 fixed, M5 at 0.10 becomes the next layer that DR has to clean up; M4-M9 at
0.25-0.4 is the next thing to test. The R22 budget gate must then be measured at the corrected capacity, because the
0.25 / 0.10 capacity made the gate optimistic. Then the die ladder (R28: h125) should be re-run from h100.
