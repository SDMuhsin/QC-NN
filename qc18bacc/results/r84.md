- Delay calc, derate, SI, CRPR and the data net agree within 0.7 ps [M].  Both timers: CRPR on, SI on, CCS receiver model
  (ICC2 TIM-050 "PrimeTime Delay Calculation, SI, Timing Window Analysis, CRPR"; PT rc_receiver_model_mode advanced).
- Cause 1 (launch, -7.3 ps) [M][S]: the IO latency DEFINITION differs.  ICC2 compute_clock_latency (run by us in qb_io_lat
  and automatically inside route_opt, man page) = median over "io pair regs" only (9289 register clock pins, d7.txt
  -verbose; wcl early 0.6639 / late 0.7375 on the eco label).  PT qb_clk_arrival = p50 over ALL 26132 register clock pins
  (wcl early 0.670 / late 0.742).
- Cause 2 (capture, -3.8..-4.2 ps) [M]: PT's clock arrives later; attributed [E] to the fill-aware SPEF PT reads (R68), ICC2
  times the unfilled route.  This makes PT MORE pessimistic for hold, so it does not explain the excess ICC2 violators.
- Net: ICC2 is pessimistic by ~3.3 ps on port -> flop hold, about cause 1 minus cause 2.  route_opt does NOT fix these
  (r82: 104-111 left at about -1.5 ps), so this over-pessimism costs no hold cells at wcl [M].
- NOT fixed at source.  compute_clock_latency has no options except -verbose [S, h.log], and route_opt re-runs it
  internally, so ICC2 cannot be given PT's definition with a one-line change.  To align them, one of two things must happen:
  (i) ICC2 IO latency set explicitly from a p50-of-all-registers measurement, with the automatic update turned off; or
  (ii) PT qb_clk_arrival restricted to IO-pair registers.  Each changes a sign-off constraint definition (PI decision).
