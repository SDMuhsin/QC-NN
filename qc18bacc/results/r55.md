## Item 1: PT vs ICC2 slew / cap gap  -- root cause found [M]
- Not the libraries: ICC2 NDM and PT both read `tcbn65gplus{wc,tc,lt}_ccs.db` (libs.tcl / col_blk.tcl both call `qc_db`;
  PT log `Loading db file .../CCS/.../tcbn65gpluswc_ccs.db`). Not the parasitics: the same net has wire C 0.0226 pF in PT
  (SPEF, annotated) and ICC2.
- PT (`report_capacitance_use_ccs_receiver_model = true`, `rc_receiver_model_mode = advanced`) loads each input with its
  CCS receiver capacitance: n1690 (NR2D2 -> 33 loads) pin cap min 0.0344 / max 0.0674 pF (AOI22D1/B1 0.00103 vs 0.00179 pF:
  receiver_capacitance2 at the 0.66 ns input slew), total max 0.090 pF.
- ICC2: `time.enable_ccs_rcv_cap` (block scope) defaults to **false**; ICC2 then uses the scalar pin cap.
  [M] r54 route block, same net, func_ss, one toggle (`$B/icc2/col/r55diag/rcv.tcl`):
  | ICC2 timer | n1690 load | U1899/ZN slew | report_constraints DRV (all scenarios) |

  | enable_ccs_rcv_cap true | 0.09 pF | 0.66 ns | 3 049 (ss max_tran lines 17 213, max_cap ss/tt/ff 2 030 / 1 472 / 1 032) |
  PT r54: 0.09 pF / 0.66 ns on the same net, 16 483 / 1 010 ss violators -> ICC2 now reproduces PT.
- Fix: `qb_timer` in flow/icc2/common.tcl (called by init and every `qb_open` step, outputs) sets the option, so
  place_opt / clock_opt / route_opt optimise against the receiver model PT signs off with. Re-run from place.

- ff hold (bin 2 of r54) is a second, independent cause [M]: same path in both tools on the r55 pass-1 route

## Open items (not closed by 05:00; nothing hedged)
1. Residual ss DRV / ff hold. ICC2 and PT now see the same violations (ss DRV: 98 / 98 pins identical on pass 1;
   ff hold path: same numbers to 0.1 ps except CRPR). Two measured mechanisms:
   - route_opt optimises on its pre-ECO-route timing. It ends there at HOLD-COST 0 / LDRC 7, after an area-recovery phase
     (cells 207 350 -> 206 935) that leaves min-size drivers at the limit (ND2D1 / BUFFD1 / CKBD1 / DFQD1, fanout 14-17,
     0.04-0.07 pF, driver slew 0.41-0.50 ns). Routing its changes plus the final extraction then put load pins at 0.51 ns
     and flop pairs at -1..-2 ps. Same counts with the receiver model on or off in the optimiser view (drvq2: rcv off 14
     DRV nets / 168 hold, on 9 / 22), so this is not a model mismatch.
   - PT's CRPR threshold cannot go below 1 ps (0 / 0.5 are clamped to 1; PBA path / exhaustive give the same CRPR).
     So pessimism of 1 ps or less on the leaf common pin is never credited (t0_reg_14 -> t1_reg_14: PT credit 0.1 ps vs
     ICC2 1.7 ps; slack PT -2.2 vs ICC2 -1.2 ps). That is why PT counts more hold endpoints than ICC2 (239 vs 68).
   Next step (needs a decision, not taken here): a closure method that is not a repeated route_opt / PT-ECO loop, e.g.
   stopping route_opt's area recovery from consuming the last DRV slack (option not found in Q-2019.12 route_opt.*), or
   one sign-off PT ECO (fix_eco_drc / fix_eco_timing -type hold) applied by ICC2 eco routing.
2. Dummy fill is not in the timing extraction: ICC2 extraction / PT SPEF see no fill (floating M1-M7 fill adds some
   coupling cap). The kit has no StarRC nxtgrd for 6X2Z.
3. M8 / M9 density belongs to the chip top (the block has no M8 / M9 metal).
