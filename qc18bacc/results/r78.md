## Predictions (PI) [M on the r77 route netlist + parasitics, PT with the R78 contract; r78b not yet at the ECO]

- (a) act -> act_o hold bin to 0: does NOT hold.  With act_o -min = -(Le + 0.95 Tq) the slack is, by construction,
  FT min delay - hold uncertainty (QC_UNC_HOLD 0.05 ns, applied by both tools on the port-to-port path).  The QB5_FT
  (BUFFD4) min delay is 0.022 ns (ff) / 0.026 ns (ml) (r77 pt_blk feedthrough_delay min), so every bit whose act -> act_o
  min delay is < 0.05 ns violates: PT ff 1133 -> 542, ml 382 -> 76 feedthrough endpoints, worst -0.028 ns (act[841]).
  The bin shrinks but cannot reach 0 while the next column's hold uncertainty is charged again on this column's
  feedthrough.  Counting it once (on the next column's capture flop) is a contract change = PI decision; I did not add
  an uncertainty term to the output delay (it would read as a margin).  The setup bin A follows: ICC2 still has to put
  delay on the act branch, which at the 5.0 ns P&R period conflicts with act -> act_o setup (r78b cts wcl 689 setup
  violators, -0.02 ns, all scenarios' Le / Lc as intended).
- (b) PT pre-ECO hold count drops > 10x: does NOT hold.  The tools already correlate per endpoint (same worst 5, 1-3 ps);
  the R78 contract gives ff 1243 -> 652 (1.9x), ml 494 -> 188 (2.6x), ss_rcw 4 -> 4.  The remaining ~110 non-FT ff /
  ~112 ml endpoints (act -> reg, pw / pf / s_rd / w_r -> reg) are seen by ICC2 too and left by route_opt (open below).
- (c) ECO max_transition at g_r_6 u_acc disappears: not measured (r78b did not reach the ECO before the hard stop).
- (d) ECO converges in <= 2 rounds: not measured; (a) / (b) imply a hold ECO of hundreds of buffers again.
