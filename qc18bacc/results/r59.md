## Bugs
1. **route_opt hold: the report was partly wrong. route_opt does fix hold.** [M] The r55 netlist has 122 `ropt_h_inst`
   buffers. The hold step has no "Phase" line: it shows up only in the "optimization complete" row (HOLD-COST
   0.33 -> 0.00, +122 cells). It fixes against parasitics from before route_opt ECO-routes its own changes, and that
   ECO routing leaves ps-level misses (145 -> 76). analyze_design_violations bins all of the rest as H8 "small"
   (< 5 ps). The hold-purpose lib cells are fine (613 cells, BUFFD1 included), CRPR is on, and 2019.12 has no
   route_opt hold option (man pages checked). **Fix:** `icc2/route.tcl` runs a second incremental `route_opt` (the
   Synopsys RM pattern): 76 -> 25 -> 23 ICC2 [M].
2. **ss max_transition has two causes.** (a) One route_opt pass did not converge: LDRC was stuck at 50 in r55. The
   flop-driven fanout-17 `cbr[*]` nets at 0.501-0.511 ns are fixable: upsizing DFQD1 to DFQD2 cleared one [M], and
   analyze_design_violations has 7 of 11 uncategorised. The second route_opt takes them to 0 [M] (same fix as 1).
   (b) The decap/filler insertion after route_opt (`qb_fillers`, 272 k cells) adds about 0.4 % cap to these
   borderline nets (cbr[728] 0.04976 vs 0.04956 pF). With the fillers removed in memory, ICC2 ss tran goes from
   22 pins to 0 [M]. The PT ECO's fix_eco_drc clears the rest (18/5 -> 0/0) [M]. I did not change the filler order.
3. **ICC2 vs PT on ff hold: the OCV suspicion is wrong.** PT is already `analysis_type on_chip_variation` with CRPR on
   (report_design) [M], and `set_operating_conditions -analysis_type on_chip_variation` leaves 239 unchanged [M].
   The real cause is PT's CRPR threshold floor. `timing_crpr_threshold_ps` is already 1 ps, and setting it to 0 or
   0.1 reads back 1 [M]. On the shared leaf `cts_inv_32229529`, PT's early/late split is only 1.0 ps, below that
   floor, so PT credits 0.06 ps while ICC2 credits 1.6 ps (same path: PT -2.8 ps, ICC2 -1.8 ps) [M]. That is a
   systematic ~1 ps on direct DFQD1 Q->D paths, which is why PT finds 173 and ICC2 23. There is no native PT setting
   below 1 ps. I documented this in `signoff/pt/common.tcl`. Not fixable without a margin, so it stays open.
4. **Residual after the PT ECO: 5 ff endpoints, -2.5 to 0 ps** [M]. All are direct DFQD1->DFQD1 paths with
   CRPR <= 0.3 ps. None of the 5 is in `pt_eco.tcl` or `hold_unfixable.txt` [M], so PT saw them passing before the
   ECO. Bin: 5/5 "ICC2 ECO legalise/route perturbation of untouched neighbours" (the R56 mechanism), stacked on the
   ~1 ps floor from 3. No margins and no frozen nets were used.
5. **IO budget shift: not a bug.** [M] After `compute_clock_latency` (cts.tcl), ICC2 launches and captures the IO
   paths at the ideal network latency (ss act[0] -> act_o[0]: "clock network delay (ideal) 0.81" on both edges).
   That is PT's +L / -L shift. What remains is the latency estimate: ICC2 0.805/0.534/0.386 against PT p50
   0.712/0.474/0.345 (ss/tt/ff), at most 0.09 ns, with IO slack >= 0.2 ns. init/place (L=0) use ideal clocks, which
   is correct.
6. **5610 unannotated nets: benign.** [M] Of the 5433 listed, all have no driver and 0 loads (dangling DC nets, for
   example `g_s34_s3[*]`). No timing arc uses the wire-load fallback.
7. **Second ECO round on the wrong label: fixed.** `icc2/outputs.tcl` writes `out/label.txt` (the label it wrote
   from). `blocks/col/run.sh eco` sets `QB_ECO_FROM` from that file for PT (`QB_ECO_BLOCK`) and for ICC2.
   `icc2/eco.tcl` opens `qb_open $QB_ECO_FROM eco`, and `qb_open` (icc2/common.tcl) reopens without a copy when
   from = to. Round 1 (r59) used route [M]. Round 2 has not been run yet.
